# Задание 3. Список требований для внешних интеграций систем домофона и шлагбаума

## 1. Функциональные требования.

 - Удаленное управление: Возможность открыть дверь/шлагбаум через внешнее приложение.
 - Классический домофон: открытие двери/шлагбаума по звонку.
 - Видеопоток: Возможность смотреть онлайн видео поток с камеры домофона/шлагбаума.
 - Система должна предоставлять альтернативные способы доступа (магнитный ключ, код).
 - Гостевой доступ: Генерация временных кодов доступа через систему УК.
 - Журналирование: Логирование всех действий (кто, когда и как вошел/проехал) для последующего аудита безопасности.
 - Видеоархив: Просмотр архива видео.
 - Автоматическое открытие двери: распознавать пользователя по биометрии (по лицу) и автоматически открывать дверь, если ему разрешён доступ в дом.
 - Автоматическое открытие шлагбаума: Открыть доступ, если распознан номер автомобиля, которому въезд разрешён.

## 2. Требования к информационной безопасности.

 - Сетевая изоляция: Оборудование и серверы должны находиться в отдельной локальной сети изолированной от чего-либо остального.
 - Сетевая доступность: Сеть для оборудования и серверов должна иметь защищенный доступ через Интернет VPN.
 - Шифрование трафика: Использование протокола HTTPS/TLS (версия 1.2 и выше) для взаимодействия между устройствами, сервисами и мобильными приложениями.
 - Уникальные учетные записи: Запрет на использование заводских логинов и паролей (admin/admin). Каждое устройство и оператор должны иметь свои реквизиты.
 - Двухфакторная аутентификация (2FA): Обязательна для административного доступа к серверу управления интеграцией и личным кабинетам сотрудников УК.
 - Механизм обезличивания: Например, токенизация. Внешний сервис работает только с токеном. Сопоставление токена и персональных данных происходит только на стороне Системы ЖКХ.
 - Разграничение прав: Система должна поддерживать ролевую модель. Собственник видит только свой звонок и т.д.
 - Отключение лишних сервисов: На домофонах и контроллерах должны быть закрыты неиспользуемые порты (Telnet, FTP).
 - Журналирование: Логирование всех действий (кто, когда и как вошел/проехал).
 - Целостность логов и архивов: Защита от несанкционированного удаления или редактирования с помощью хеширования.
 - Номера автомобилей и журналы событий: Должны шифроваться при хранении на серверах и конечных устройствах с использованием стойких алгоритмов.
 - Физическая защита оборудования: Физический доступ к оборудованию должен быть ограничен.
 - Защита хранимых данных: Биометрические шаблоны хранятся исключительно в ЕБС в соответствии с законом. 
 - Локальный кэш (при использовании Edge AI): должны применяться методы необратимого шифрования или гомоморфного шифрования, позволяющего сравнивать данные, остающиеся в зашифрованном виде.
 - Zero Trust архитектура: Принцип «никому не доверяй, проверяй всегда» означает обязательную проверку подлинности и прав для каждого запроса на доступ, независимо от его источника (внутренняя сеть или интернет).


## 3. Протоколы аутентификации и авторизации.

### Аутентификации устройств (Device-to-Server, Device-to-Device).
Этот уровень гарантирует, что взаимодействуют только доверенные компоненты системы: домофон, шлагбаум, сервер управления, облачный сервис.
Протокол: Mutual TLS (mTLS) с сертификатами X.509. Взаимная аутентификация TLS требует, чтобы и клиент (устройство), и сервер представляли и проверяли цифровые сертификаты во время рукопожатия.
   Управление жизненным циклом сертификатов осуществляется через инфраструктуру открытых ключей (PKI).


### Аутентификации пользователей.
Этот уровень отвечает за проверку личности человека (для домофона) или транспортного средства (для шлагбаума).
Согласно Федеральному закону от 29.12.2022 № 572-ФЗ, осуществление идентификации и аутентификации физических лиц с использованием биометрических персональных данных 
должно проводиться с использованием государственной информационной системы "Единая система идентификации и аутентификации" (Единая биометрическая система, ЕБС). 
Это означает, что биометрические шаблоны (контрольные образцы) граждан должны храниться в ЕБС, а не в локальной базе данных домофона.
Организации, предоставляющие сервисы с биометрической аутентификацией, обязаны интегрироваться с ЕБС, либо непосредственно используя её, либо взаимодействуя с ней для получения векторов.

### Авторизация пользователей.
Уровень авторизации определяет какие действия разрешены данной сущности.
Основной протокол: OAuth 2.0 с использованием JWT-токенов доступа. 
Клиент после аутентификации получает токен доступа в формате JSON Web Token, который содержит утверждения (claims) о правах доступа (scope). 
Этот токен предъявляется серверу ресурсов для совершения действия.

Модель контроля доступа: Атрибутный контроль доступа (ABAC). 
Решение о доступе принимается на основе оценки множества атрибутов (роль пользователя, время, день недели, местоположение устройства) согласно предварительно заданным политикам. 

### Защита канала связи. 
Все коммуникации между устройствами, серверами и облачными службами должны быть защищены с помощью TLS версии не ниже 1.2


## 4. Взаимодействие между системой предприятия и внешней платформой.

### Биометрическая аутентификация (домофон): Интеграция с ЕБС.

Сценарий 1 (Обязательный): Домофон выполняет захват и предварительную обработку изображения лица, после чего зашифрованный биометрический образец (или вектор признаков) передается на сервер системы. Сервер взаимодействует с API ЕБС для верификации «1:1» (при наличии идентификатора, например, номера квартиры) или идентификации «1:N» (поиск в базе жильцов). Решение о предоставлении доступа принимается на основе ответа ЕБС. Это обеспечивает прямое соответствие закону № 572-ФЗ .

Сценарий 2 (Edge AI с синхронизацией): Для повышения скорости работы и обеспечения функционирования при отсутствии связи может применяться гибридная модель. На устройстве (Edge) работает нейросетевая модель, преобразующая лицо в вектор признаков. Сравнение происходит локально с зашифрованной базой эталонных векторов, предварительно синхронизированной из ЕБС или централизованной системы управления объектом. Локальное хранение биометрических шаблонов должно использовать необратимые преобразования (cancelable biometrics) или гомоморфное шифрование для защиты от компрометации данных на устройстве .

### Распознавание номеров.
Камера ANPR (Automatic Number Plate Recognition) распознает номер в реальном времени (за 1-2 секунды).
Распознанный номер (как строка) не должен передаваться или храниться в открытом виде.
Рекомендуемый подход: Преобразование номера в криптографический хеш (с использованием соли) и проверка этого хеша против «белого списка» доверенных хешей, хранящегося локально на контроллере шлагбаума или на защищенном сервере. Это минимизирует риски утечки персональных данных.

### Одноразовые пароли (TOTP).
Для предоставления временного гостевого доступа могут генерироваться одноразовые коды по алгоритму RFC 6238 (TOTP).
